# 博文写作与发布 SOP

> 适用范围：`laoola.github.io` 的新增博文、实质性修订和发布验收。
>
> 核心目标：内容真实、步骤可复现、链接可访问、构建可验证、发布可追溯。

## 1. 强制原则

1. **真实优先**：只写作者实际做过、读过或验证过的内容。AI 可以协助整理结构和语言，但不得编造作者经历、实验过程、报错、数据或效果。
2. **证据优先**：关键结论尽量对应命令、代码、原始报错、截图、日志或官方资料。
3. **公开边界**：发布前检查公司名、客户信息、运营数据、内部地址、账号、令牌、Cookie 和其他敏感内容；不确定能否公开时先询问作者。
4. **公司相关题材先审后写**：素材涉及公司项目的代码、数据、真实案例、架构、算法、参数、故障或性能信息时，先向作者提交选题、公开范围、证据来源和脱敏方案。只有作者明确审核通过后才能开始写素材卡、大纲或初稿；授权仅适用于当次明确范围。仅删除公司名、改变量名或替换 IP 不等于完成脱敏。
5. **先验证后发布**：文章没有完成本地验证，不进入提交和发布环节。
6. **流程随仓库走**：技术栈、命令或发布方式变化时，同步更新本 SOP 和根目录 `AGENTS.md`。

## 2. 流程总览

| 阶段 | 主要产出 | 进入下一阶段的条件 |
| --- | --- | --- |
| 选题 | 读者、问题、预期收获 | 主题明确，属于博客定位 |
| 公开审查（仅公司相关题材） | 公开范围、证据来源、脱敏方案 | 作者明确审核通过；未通过不得开始写作 |
| 素材 | 场景、环境、过程、结果、证据 | 关键事实可核对，公开边界明确 |
| 草稿 | 分类目录、Markdown 文件、Frontmatter | Schema 完整，`draft: true` |
| 写作 | 结构完整、步骤可复现的正文 | 没有虚构内容和待确认的关键事实 |
| 自检 | 内容、链接、图片、标签检查 | 自检问题已处理 |
| 本地验证 | 构建报告、链接检查、浏览器验收 | `npm run verify` 通过，页面实测正常 |
| 审查提交 | 审查结论、明确暂存的变更、提交 | 作者确认提交，审查无阻断项 |
| 发布验收 | Actions 结果、线上页面和索引检查 | GitHub Pages 部署成功，线上功能正常 |

## 3. 选题与素材准备

开始写作前，先形成一张素材卡。素材不全时可以列待办，但不能用想象补齐。

```text
主题：
目标读者：
读者要解决的问题：
真实场景：
软硬件及版本环境：
原始报错或需求：
实际尝试过程：
最终方案：
验证命令与结果：
适用范围及未解决问题：
代码、日志、截图等证据：
参考资料：
不得公开的信息：
```

### 不同文章的最低素材要求

- **问题排查**：必须有问题现象、环境、关键报错、定位过程、解决方案和验证结果。
- **工具教程**：必须有版本、安装或配置前提、实际操作步骤、验证方法和常见边界。
- **经验总结**：必须区分事实、个人判断和尚未验证的推测，不把个案包装成普遍结论。
- **系列文章**：先明确总览、分篇顺序和读者路径，再检查各篇之间的链接与术语一致性。

## 4. 建立文章文件

### 4.1 文件位置

```text
src/content/blog/<分类>/<文章-slug>.md
```

- 必须放在分类子目录，不直接放在 `src/content/blog/` 根目录。
- 新分类和新文件名默认使用**小写英文 kebab-case**。
- 文件名不带日期前缀，发布日期由 Frontmatter 管理。
- 存量中文文件名不批量改名；确需修改 URL 时单独评估旧链接影响。
- `slug` 发布后保持稳定。只改标题通常不需要改文件名。

### 4.2 Frontmatter 模板

```yaml
---
title: "一个具体、可检索的标题"
description: "说明文章解决什么问题，以及读者能获得什么。"
date: 2026-11-04
tags: ["Qt", "Linux", "Wayland"]
draft: true
# updated: 2026-11-05
---
```

将示例日期替换为实际日期。

| 字段 | 要求 |
| --- | --- |
| `title` | 必填；具体、自然，包含读者可能搜索的核心对象或问题 |
| `description` | 必填；用一两句话概括问题和收获，不堆砌关键词 |
| `date` | 必填；首次发布日期，后续修订不随意改变 |
| `tags` | 建议 3–5 个；优先复用已有标签，避免同义词和大小写变体 |
| `draft` | 草稿阶段设为 `true`；发布验收前改为 `false` |
| `updated` | 可选；只有实质性修订才更新，修正个别标点不必更新 |

## 5. 正文写作

### 5.1 推荐结构

问题排查和技术教程通常按以下顺序组织：

1. **场景与问题**：谁遇到什么现象，为什么值得解决。
2. **环境与前提**：系统、软件、版本、配置和必要条件。
3. **分析或方案**：关键判断、原因和解决思路。
4. **实施步骤**：代码、命令和配置保持完整，说明执行位置。
5. **验证结果**：给出实际命令、输出或现象，不只写“测试通过”。
6. **边界与注意事项**：不支持的场景、已知限制和未解决问题。
7. **参考资料**：优先引用官方文档、源码或原始资料。

不是所有文章都要机械使用七个标题。结构应服务内容，但“怎么做”和“如何验证”不能省略。

### 5.2 写作规则

- 开头直接交代真实问题和读者收益，避免空泛的背景铺垫。
- 命令、参数、路径、类名和版本号必须核对；示例代码尽量实际运行。
- 区分原始事实、推测和观点；未验证内容明确标注。
- 不为凑篇幅重复结论，不使用夸张承诺或营销口号。
- AI 参与时，作者必须复核技术事实、语气和个人经历；不得虚构“我做过”的过程。

### 5.3 链接与图片

- 站内文章链接使用从站点根目录开始的**绝对路径**，保留尾斜杠：

  ```markdown
  [文章标题](/blog/category/article-slug/)
  ```

- 不使用 `./文章名`、`../分类/文章名` 等相对文章链接。
- 中文 URL 保持原样，ASCII 字母使用小写，以匹配 Astro 的文章 ID。
- 外链使用有意义的文字，不写“点击这里”；外部链接需要人工抽查，自动链接检查只覆盖站内链接和资源。
- 图片放在 `public/images/blog/<文章-slug>/`，使用描述性文件名和准确的替代文本。
- 截图发布前裁掉或遮盖账号、域名、内部地址、通知内容等敏感信息。

## 6. 标签、搜索与 SEO

- 每篇文章建议使用 3–5 个标签，优先复用已有标签，不为增加曝光堆标签。
- 标签应描述文章主题，不把标题中的每个词都变成标签。
- 文章标题、描述、Canonical、Open Graph、RSS 和 Sitemap 由现有布局与构建流程生成，不为单篇文章手工伪造。
- `updated` 表示内容实质变化，不等于每次构建时间。
- 发布前将 `draft` 改为 `false`，否则文章不会进入正式页面、RSS、Sitemap 和 Pagefind 索引。

## 7. 本地验证

### 7.1 自动验证

首次拉取或依赖变化后先执行：

```bash
npm ci
```

发布前必须执行：

```bash
npm run verify
```

通过标准：

- `astro check`：0 errors、0 warnings、0 hints。
- Astro 生产构建成功。
- Pagefind 索引成功，新文章处于非草稿状态并进入索引。
- 站内链接与资源检查无缺失目标。

### 7.2 浏览器验收

```bash
npm run preview -- --host 127.0.0.1
```

至少检查：

- [ ] 首页和博客列表能看到新文章，标题、描述、日期正确。
- [ ] 文章正文没有异常换行、乱码、错误代码块或失控的长内容。
- [ ] 文章内目录、代码复制等已有交互功能正常。
- [ ] 站内文章链接和标签链接可用，没有 404。
- [ ] 搜索文章标题或关键词能找到新文章，结果不混入首页和列表页。
- [ ] 深色与浅色主题下正文、代码、图片和链接可读。
- [ ] 至少检查一次窄屏或移动端布局。
- [ ] Canonical、文章时间和分享信息与 Frontmatter 一致。

验证结束后关闭预览服务和本会话浏览器，不遗留后台任务。

## 8. 审查、提交与推送

1. 先向作者展示文章和验证结果，得到明确的提交或发布确认。
2. 提交前进行代码与内容审查：技术事实、公开边界、链接、Frontmatter、项目规范和意外改动。
3. 检查完整变更，而不是只检查新文章：

   ```bash
   git status --short
   git diff
   ```

4. 按明确文件路径暂存，不使用 `git add -A` 或 `git add .`。
5. 暂存后审查完整待提交变更，确保新文章和其他未跟踪文件也已纳入：

   ```bash
   git diff --cached
   ```

6. 文章内容与无关工程改动尽量拆成独立提交。
7. 提交信息使用简洁祈使式主题，例如：

   ```text
   docs: 新增 Qt Wayland 输入问题排查博文
   ```

8. 按仓库当前分支策略提交和推送。当前 GitHub Pages 由 `main` 分支的推送触发部署。

## 9. 线上验收

推送不等于发布完成。必须继续检查：

- [ ] GitHub Actions 部署成功。
- [ ] 新文章线上 URL 返回正常页面，不是 GitHub Pages 404。
- [ ] 首页、博客列表、标签和搜索能发现新文章。
- [ ] 文章内链接、图片和代码块在线上正常。
- [ ] RSS 和 Sitemap 包含新文章。
- [ ] 页面标题、描述、Canonical 和分享信息正确。

若部署失败或线上页面异常，先记录实际错误，再修复并通过新的提交发布；不要把“已推送”汇报为“已上线”。

## 10. 更新与下线

- 修订文章时保留原 `date`，实质性更新再设置或调整 `updated`。
- 修改技术结论时同步修订相关命令、代码、截图和参考链接，避免正文自相矛盾。
- 修改文件名、分类或 slug 会改变 URL；必须检查所有引用并验证旧链接影响。
- 下线文章会产生旧 URL 失效风险，必须单独确认，不用 `draft: true` 悄悄代替下线方案。

## 11. 完成定义（DoD）

只有以下项目全部满足，才算一次完整的博文发布：

- [ ] 内容来自真实素材，技术事实和公开边界已复核。
- [ ] 分类、文件名、Frontmatter 和标签符合规范。
- [ ] 正文结构完整，步骤与验证结果可复现。
- [ ] 站内链接使用绝对路径，图片和参考资料可访问。
- [ ] 发布文章已设置 `draft: false`。
- [ ] `npm run verify` 全部通过。
- [ ] 本地浏览器验收通过，后台服务已清理。
- [ ] 提交前审查无阻断项，作者已确认提交。
- [ ] GitHub Actions 部署成功。
- [ ] 线上页面、搜索、RSS 和 Sitemap 验收通过。

> 如果作者只要求写作或修改而不要求提交，则完成到对应阶段即可，但必须明确说明尚未提交、尚未部署。
