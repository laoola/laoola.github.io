一个记忆主题最初的索引是「立项流程 + 分发定位」。

接下来的三天里，我又追加了几次进展。索引先后变成「双路提取实机验证收口」和「PRD 红线入模板，两仓补录」。

正文里的立项规则一条没少，但下次打开新会话，我只能从索引看到最后一次追加的内容。这个主题原本是干什么的，反而看不出来了。

问题不是正文记得不够多，而是我把三种性质不同的信息都塞进了「记忆」：长期有效的规则、已经验证的事实，以及每天都在变化的工作进度。

## 规则、事实和状态，不是一回事

我现在把它们分成三层：

| 信息 | 回答的问题 | 存放位置 | 更新方式 |
| --- | --- | --- | --- |
| 行为规则 | 以后应该怎么做？ | `AGENTS.md`、SOP | 修改规则本身，不保留一堆过期指令 |
| 长期事实 | 当时确认了什么？踩过什么坑？ | 主题记忆文件和记忆索引 | 追加新结论，保留稳定摘要 |
| 当前状态 | 现在做到哪了？下一步是什么？ | `STATUS.md` | 随实际进度更新 |

三者最重要的区别是**有效期**。

规则在被修改前一直生效；事实记录某个时间点的结论，可能随着代码变化而过期；状态则只应该描述当前这一刻。

混在一起的后果很直接：新会话可能把「昨天准备改某个文件」当成「今天仍然要改」，也可能只看到最后一次进度，找不到真正需要遵守的规则。

## append 是怎么侵蚀索引的

我当时使用的 project-memory 版本中，`memory_write(mode=append)` 会做两件事：

1. 把新内容追加到主题正文。
2. 把 `MEMORY.md` 中该主题的索引行替换成这次调用的摘要。

如果摘要写的是「完成了什么」，索引就会逐渐变成最近动态的流水账。

问题形式如下：

```text
# 不稳定：每次追加都改变主题的定位
插件开发基线 — PRD 红线入模板，两仓补录

# 稳定：索引始终说明这个主题管什么
插件开发基线 — 插件立项、开发与分发规则；最新进度见 STATUS.md
```

这是我在当时版本上观察到的行为，不代表之后的实现没有变化。不过，即使工具明天修改了实现，这条原则仍然成立：**索引是地图，不是变更日志。**

我的处理方式有三条：

- 重要主题正文顶部保留一段总则，追加内容只放后面。
- 索引摘要写「这个主题是什么、什么时候该读」，不写「最后一次做了什么」。
- 当前阶段和下一步只放进 `STATUS.md`，不靠主题索引承载。

## 我的写入路由

现在记录一条信息前，我会先看它像哪句话：

| 信息长什么样 | 去哪里 |
| --- | --- |
| 「以后每次都要……」「不允许……」 | `AGENTS.md`；复杂流程放进 SOP |
| 「已经确认……」「这个问题的原因是……」 | 当前项目或全局记忆的主题文件 |
| 「目前正在……」「下次从这里继续……」 | `STATUS.md` |
| 「密码是……」「令牌是……」 | 不写入记忆，只记录凭据的安全存放位置 |

作用域也要分开：只属于一个项目的事实放项目记忆，跨项目的本机工具链结论放全局记忆。

一条消息同时包含规则和事实时，不应该整段塞进同一个文件。比如「以后提交前必须审查，这次审查发现 README 过期」，前半句是行为规则，后半句是本次审查结果，应该拆开处理。

## 这次博客改造中的实际例子

最近我给博客增加了一条规则：公司相关题材必须先经我明确审核通过，才能开始写。

这条要求最后没有只留在某次对话里，而是分成了三处：

```text
博客仓库/
├─ AGENTS.md                         # 强制规则与入口
└─ docs/运维/博文写作与发布流程.md   # 完整写作和发布流程

项目记忆/
├─ MEMORY.md                         # 主题索引
├─ laoola-blog-writing-sop.md        # SOP 的位置和维护约定
├─ laoola-blog-topic-plan.md         # 已确认的六篇选题与授权裁决
└─ STATUS.md                         # 当前写作进度和下一步
```

仓库文件负责约束行动，项目记忆负责跨会话找到这些约定，`STATUS.md` 负责告诉我现在写到哪一篇。

这样即使以后换了一次会话，也不需要把整段历史对话重新读一遍。

## 记忆不是越多越好

我现在会主动放弃几类内容。

**一次性的操作过程不记。** 命令跑过、文件读过、页面打开过，这些信息完成任务后通常就没有长期价值。

**原始会话记录不默认翻。** 它体量太大，只有明确需要追查历史时才读取。

**与当前代码冲突的旧结论不继续沿用。** 记忆只是历史快照，代码、规格和当前文档才是事实源。发现冲突时，应该标明旧记忆已经过时，而不是替它找理由。

**凭据不记明文。** 「密码放在某个密码管理器里」可以记，密码本身不进入记忆文件。

另外，**上下文压缩不等于长期记忆**。压缩解决的是当前会话太长，记忆解决的是换会话后还能找到重要结论。一个保留任务的近期脉络，一个保留经过筛选的长期信息。我之前整理过 [strategic-compact 上下文压缩配置](/blog/claude-code/strategic-compact配置/)，两者可以配合，但不能互相替代。

## 新会话的检查清单

现在判断这套系统有没有正常工作，我会检查六件事：

- [ ] 只看一行索引，能否判断这个主题该在什么时候读？
- [ ] 连续追加几次后，主题索引是否仍然稳定？
- [ ] 行为规则是否有明确的权威来源，没有在多份文档里分叉？
- [ ] 当前进度是否只在 `STATUS.md` 更新，没有多处互相矛盾？
- [ ] 旧记忆与当前代码冲突时，是否明确以代码为准？
- [ ] 记忆和索引中是否都没有明文凭据和不必要的内部信息？

对我来说，记忆系统的目标不是让 AI 记住所有事，而是让它在新会话里少问一次已经回答过的问题，同时不把过期结论当成今天的事实。

**规则进文档，事实进记忆，进度进 STATUS。剩下的，宁可不记。**
