我曾经把 AI 提交前的检查简化成两件事：测试通过，`git diff` 里没有敏感信息。

后来在个人博客的一次文档提交中，构建和类型检查全部通过，审查却仍然拦下了两个问题：新增文章没有进入原来的 diff 审查范围，SOP 文件名还违反了已经确定的命名规则。

这两件事都不会让测试失败，却足以让一次提交留下长期麻烦。

从那以后，我把“能不能跑”和“该不该进入 Git 历史”分开处理。后者至少需要四道门禁。

## 门禁一：同时审查规范与需求

只看代码实现，很容易陷入“它能运行，所以应该没问题”的误区。我现在把提交前 review 分成两个轴：

| 审查轴 | 核心问题 |
| --- | --- |
| Standards | 是否符合仓库已经成文的命名、目录、文档、命令和工程规范？ |
| Spec | 是否实现了用户确认的需求？有没有遗漏、超范围或未经批准的公开内容？ |

博客 SOP 初稿曾命名为 `博文写作与发布SOP.md`。从内容看没有问题，但 Standards 审查发现，文档命名规则要求使用中文描述并避免大写缩写，于是改成：

```text
博文写作与发布流程.md
```

随后还要同步修改 README、AGENTS.md 和记忆中的入口，并全文检索旧文件名。只改文件名、不改引用，不算修复完成。

Spec 则关注另一件事：这次提交到底应该包含什么。依赖升级、标签调整、文档改动看起来都可能“有用”，但如果不在用户确认的范围内，就不能借一次提交悄悄带入。

发现阻断项后，流程不是“先提交，后面再补”，而是：

> 修复 → 针对问题复核 → 阻断关闭 → 才允许暂存和提交。

## 门禁二：提交范围不等于整个工作树

AI 在一个已有工作树里工作时，可能同时看到本次修改、历史遗留修改和未跟踪文件。最危险的一句话是：“反正都是这个仓库的改动，一起提交吧。”

我的默认范围是：**只提交当前对话产生、并经过确认的修改。**

先检查：

```bash
git status --short
git diff
```

然后按明确路径暂存：

```bash
git add -- README.md AGENTS.md src/pages/about.astro
```

我禁止 Agent 使用：

```bash
git add -A
git add .
```

这两个命令本身不是坏功能，但它们把“圈定提交范围”这个需要判断的动作，变成了无差别收集。工作树里只要有一个范围外文件，就可能被一起写入历史。

如果看到了不属于本次任务的修改，正确做法是列出来并保留，不是替用户决定提交、删除或还原。

## 门禁三：真正审查的是暂存区，不是工作树

这是最容易被忽略的一道。

`git diff` 默认展示的是**已跟踪文件在工作树与暂存区之间的差异**。一个尚未跟踪的新文章，可以出现在 `git status --short` 里，却不会出现在普通 `git diff` 的正文差异中。

博客 SOP 最初只写了：

```bash
git status --short
git diff
```

Spec 审查指出：这套流程覆盖不到新博文。以后如果 Agent 按文档执行，就可能在“已检查完整 diff”的错觉下提交一篇从未被正文审查的新文件。

现在流程改成了：

```bash
# 按明确路径暂存
git add -- README.md src/content/blog/dsh/new-article.md

# 看暂存统计与完整内容
git diff --cached --stat
git diff --cached

# 再检查空白错误等问题
git diff --cached --check
```

`git diff --cached --check` 只负责一类机械检查，不能代替阅读完整 diff。真正要核对的是：新增文件、删除文件、重命名、文档引用和所有待提交内容，是否都与本次授权一致。

暂存之后如果又修改了文件，还要重新检查状态。工作树和暂存区可能从此不一致，之前看过的 cached diff 不能继续当作最终证据。

## 门禁四：把“交付物齐备”变成可执行检查

另一个真实教训发生在一个插件仓库：连续完成多次功能提交后，才被问到“README 写了吗”。答案是还没有。

问题不是团队不知道 README 重要，而是规范里只有一句“文档为必答题”，验收清单却全是功能项。结果就是所有功能都通过，仍然没有人对文档是否落盘负责。

原则句必须转换成可观察的命令。例如，一个工程仓库规定 README 和 AGENTS.md 必须纳入版本控制，就可以检查：

```bash
for file in README.md AGENTS.md; do
  git ls-files --error-unmatch "$file" > /dev/null 2>&1 || {
    echo "缺少跟踪文件: $file"
    exit 1
  }
done
```

不同仓库的必备件不同。博客可能要求 README、项目规范和写作 SOP；库项目还可能要求 LICENSE、CHANGELOG、API 文档。重点不是照抄这张清单，而是把“应该有”变成“哪条命令能证明它有”。

功能验收和交付物验收应该是两组独立项目，任何一组都不能替代另一组。

## 我现在的提交流程

把四道门禁串起来，顺序如下：

| 步骤 | 要留下的证据 |
| --- | --- |
| 1. 确认授权与范围 | 用户要求提交；本次涉及的文件清单明确 |
| 2. 完整查看工作树 | `git status --short`、`git diff`，范围外文件单独列出 |
| 3. 运行项目验证 | 类型检查、测试、构建、链接检查等真实输出 |
| 4. Standards / Spec 双轴审查 | 发现项、修复结果和复核结论 |
| 5. 明确路径暂存 | 不使用 `git add -A` 或 `git add .` |
| 6. 审查待提交内容 | `git diff --cached --stat`、完整 cached diff、`--check` |
| 7. 核对标准交付物 | 用 `git ls-files` 等命令证明必需文件已跟踪 |
| 8. 提交并复核 | 简洁明确的提交信息，提交后再次查看状态 |

提交信息也应该说明“改了什么”，而不是只留下 `update`、`修改`、`调整` 这类无法检索历史的词。我通常使用 Conventional Commits 类型加中文描述，例如：

```text
docs: 新增博文写作流程并迁移项目规范
```

最后，**提交、推送和上线是三个不同状态**。本地提交成功不代表远端已更新，推送成功也不代表部署已经完成。汇报时应分别给出证据，不能一句“已完成”全部带过。

## 提交前检查清单

- [ ] 已经获得明确提交授权，没有替用户扩大范围。
- [ ] 工作树和完整 diff 已检查，范围外修改保持原样。
- [ ] 项目验证通过，失败项没有被隐藏。
- [ ] Standards 和 Spec 审查均通过，阻断项已经修复并复核。
- [ ] 只按明确路径暂存。
- [ ] 已阅读完整 `git diff --cached`，新文件也在审查范围内。
- [ ] README、规范、许可证等项目要求的交付物已按清单核对。
- [ ] 提交信息能说明具体改动。
- [ ] 提交、推送、部署状态分别汇报。

测试回答的是“系统能不能工作”，这些门禁回答的是“这次改动该不该进入历史”。AI 能加速实现，但提交前仍然需要一套不依赖自觉的检查机制。
