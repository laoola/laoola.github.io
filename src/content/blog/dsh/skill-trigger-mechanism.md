我遇到过一种很典型的困惑：`SKILL.md` 明明已经放进技能目录，用户请求看起来也和技能有关，Agent 却没有调用它，而是直接开始干活。

我最初把这理解成“语义匹配失灵”。后来检查目录注入和文件发现代码，才发现这里有两个独立环节：**文件有没有被发现，以及模型要不要触发它。**

只检查文件是否存在，会漏掉后半段问题。

## 发现不等于触发

当前 DSH 的技能链路可以简化为三步：

| 阶段 | 实际发生的事 |
| --- | --- |
| 发现 | 文件系统提供方扫描根目录，解析技能名、描述和调用配置 |
| 路由 | 模型在会话目录里看到每个技能的名称和描述，自行判断是否调用 |
| 加载 | 调用 `skill(name)` 后，才把对应 `SKILL.md` 正文交给模型 |

也就是说，常驻上下文里没有所有技能的全文。模型先看到一份摘要目录，再决定加载哪一份。

当前目录模板的核心内容就是：

```text
- `<name>`: <normalized-and-capped-description>
```

模板还明确告诉模型：用户点名，或者任务明显匹配描述时，应调用对应技能；目录只有摘要，不能在未加载正文时臆造其中的规则。

所以，这里没有一个独立的语义匹配引擎在背后自动执行技能。**是模型根据用户原话和目录描述做路由决策。**

这与[记忆分层](/blog/dsh/agent-memory-layers/)是同一个思路：常驻上下文负责定位，完整内容按需加载。

## 薄描述为什么容易导致不触发

既然模型主要依赖目录中的描述做判断，下面这种描述就几乎没有路由信息：

```yaml
---
name: task-dispatch
description: 任务管理。
---
```

它既没有说明输入是什么，也没有说明用户通常会怎么提需求。

我后来把它改成了这种写法：

```yaml
---
name: task-dispatch
description: 把已确认的需求创建为任务看板卡片。当用户说「上板 / 建卡 / 派活 / 进看板」时使用。只建卡，不代替执行。
---
```

这段描述同时回答了三个问题：

1. **做什么**：把需求创建成看板卡片。
2. **什么时候用**：用户说“上板、建卡、派活、进看板”。
3. **边界在哪**：只建卡，不执行任务。

早期做技能目录审计时，我用过“少于 40 个字符”作为薄描述的筛查线。111 个技能里筛出了 17 个，给其中 4 个实际常用的技能补上口语触发词后，目录里才能看到更明确的匹配依据。

但要特别说明：**“40 字符”不是加载器里的硬编码阈值**，只是一次审计使用的经验筛查标准。真正需要判断的是，描述有没有提供足够的路由信息，而不是机械凑字数。

## 触发词要写用户原话，不写抽象名词

技能作者容易站在能力设计者的角度写描述，用户却会用完全不同的说法。

| 抽象写法 | 更接近用户请求的写法 |
| --- | --- |
| 管理任务生命周期 | 上板、建卡、派活、进看板 |
| 诊断代理执行异常 | Agent 卡住了、任务没有进展、帮我看看为什么不动 |
| 优化界面生成质量 | 页面太像 AI 做的、去掉模板感、界面太浮夸 |
| 检查交付完整性 | 别只跑功能、检查 README、交付前核对文档 |

这些词不是为了堆 SEO，而是在给模型提供可识别的路由锚点。

我通常会把描述组织成一句话：

> 能力说明 + 典型用户原话 + 必要边界。

当然，最稳定的触发方式仍然是**直接点名技能**。用户明确指定技能时，不需要再依赖模型猜测语义相似度。

## 文件放对位置，才有机会进入目录

路由描述写得再好，文件没被发现也没有用。

我核对了当前 `@deepseek-ai/dsh-skill-filesystem` 的 `discoverRoot()`。它遍历的是扫描根目录的**直接条目**，目前接受两种形式：

```text
<root>/
├── task-dispatch/
│   └── SKILL.md       # 目录 bundle
└── quick-note.md      # 平铺 Markdown 文件
```

下面这种按分类继续嵌套的结构不会被当成技能发现：

```text
<root>/
└── 工作流/
    └── task-dispatch/
        └── SKILL.md
```

当前源码同时支持目录 bundle 和平铺 `.md` 文件，这是比旧记录更完整的事实。我的本机技能库仍统一采用 `<技能名>/SKILL.md`，因为技能经常还要携带脚本、模板和参考资料；统一 bundle 更容易维护。

这里需要记住的是：**支持平铺文件，不等于支持任意深度的嵌套目录。**

Frontmatter 也不能缺。当前发现流程要求 `name` 使用 kebab-case，`description` 必填；格式错误的条目会带着警告被跳过，模型看到的目录里只会表现为“这个技能不存在”。

## 动态刷新不代表所有内容都会立即重写

文件系统提供方会监视根目录，并在直属技能新增、删除或描述变化时让目录失效。但这里仍有几个边界：

- 只监视规定的发现深度，资源子目录的任意变化不等于技能目录变化。
- 修改描述会影响后续目录；只改正文，不会改变目录摘要。
- 已经加载到历史里的旧正文不会因为文件保存而被追溯改写。
- 已打开的界面如果仍保留旧目录，先用新会话或切换预设排除缓存因素，再怀疑触发词。

因此，验证技能修改时，我分别检查三件事：**目录里有没有、描述有没有更新、正文是不是本次重新加载的版本。**

## 给子代理派活时，我会直接点名

主会话里描述写得足够清楚，子会话仍然可能不触发。原因很现实：子会话收到的任务书、上下文长度和当前关注点都不同，它可能直接跳过可选技能，选择一条更短的执行路径。

所以给子代理写任务书时，我会明确写：

> 用 `diagnosing-bugs` 技能诊断，修复后用 `verification-loop` 技能自查。

一次点名 1–3 个真正相关的技能就够了。把十几个技能全部塞进去，只会重新制造路由噪声。

点名不是代替好描述，而是给重要流程加一道确定性约束。

## 我的排查清单

技能没有按预期加载时，我按这个顺序查：

- [ ] 文件是否位于扫描根目录的直接一层，而不是分类子目录里？
- [ ] `name` 是否为 kebab-case，`description` 是否存在且格式正确？
- [ ] 当前会话的技能目录里真的出现了它吗？
- [ ] 描述是否说明能力、典型用户原话和使用边界？
- [ ] 用户直接点名后能否加载，以此区分“发现问题”和“路由问题”？
- [ ] 修改正文后，是否重新加载或开新会话验证？
- [ ] 给子代理的重要流程，是否已经在任务书里显式点名？

最后可以把整个问题压缩成一句话：

> **发现是文件系统问题，触发是模型路由问题，正文更新是加载历史问题。**

分开排查，比反复重启和盲目堆关键词有效得多。
