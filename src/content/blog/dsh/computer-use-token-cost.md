让 AI 在 Windows 上点一个开关，最直观的办法是：截一张图，让它找到按钮，点击，再截一张图确认。

这套做法能工作，但上下文成本很高。我对比过这类任务的工具调用记录，按当时的工具链估算：

| 操作路线 | 整段任务的 token 量级 |
| --- | ---: |
| UIA 定向查找、操作、验证 | 约 1–3K |
| 截图、点击、再截图的循环 | 约 8–15K |

同一个目标，消耗差了 **5–10 倍**。

问题不是“截图没用”，而是我把截图当成了默认的感知方式。对大多数桌面控件和网页来说，AI 根本不需要先看一张完整的图片。

## 单次操作的成本差在哪

当时记录的几项单次成本如下：

| 感知方式 | 单次 token 量级 | 能得到什么 |
| --- | ---: | --- |
| UIA 定向 `find` | 约 200–800 | 控件角色、名称、状态和元素 ID |
| OCR 定向识别 | 约 100–500 | 可见文字及其位置 |
| 1080p 截图 | 约 1.1–1.6K/张 | 像素画面 |
| UIA 全树 dump，`maxNodes=1200` | 约 2–5K | 大量当前任务用不到的节点 |

有两个结论容易反直觉。

第一，**结构化信息不一定天然便宜，定向读取才便宜**。不加条件地导出整棵 UIA 树，可能比一张截图还贵。

第二，OCR 的单次成本虽然低，但它主要解决“屏幕上有哪些字”，不一定能告诉我控件角色、选中状态和可执行动作。因此不能简单按数字把 OCR 排到所有场景最前面。

真正拉开差距的是操作循环。

截图路线通常是“看 → 点 → 再看 → 再点”，每一步都产生新的图片，后续步骤还要继续携带前面的上下文。UIA 路线则可以用一次定向查询拿到元素，操作后再读取目标状态，不需要反复描述整张屏幕。

## 我的四层选路

我现在把电脑操作分成四层，而不是只有“截图”和“不截图”两种选择。

| 场景 | 首选机制 | 主要用途 |
| --- | --- | --- |
| 浏览器页面 | CDP 语义驱动 | 读取 DOM/a11y 结构，按文本、CSS 或 XPath 操作 |
| Windows 原生窗口 | UIA | 查找控件，读取状态，调用或点击元素 |
| UIA 信息缺失或稀疏 | OCR | 识别可见文字，补充定位依据 |
| 自绘界面和视觉任务 | 截图 | 判断布局、颜色、像素和画布内容 |

### 浏览器：先读结构，不看屏幕

浏览器优先走 CDP。它可以直接返回链接、按钮、输入框等语义节点，也能操作表单并读取结果，不需要把页面渲染图交给模型重新辨认。

我的常规顺序是：

1. 用 `a11y` 或 `snapshot` 读取交互结构。
2. 用语义定位执行点击、输入或选择。
3. 用 `get_value`、`wait` 或页面内容验证结果。
4. 只有需要视觉信息时才截图。

CDP 的返回成本取决于 DOM 复杂度和读取范围，所以我不给它写一个固定 token 数。原则仍然是：读目标区域，不导出整页所有细节。

### 原生窗口：UIA 定向查询优先

[Microsoft UI Automation](https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-overview) 能把桌面元素暴露为带角色、名称、属性和控制模式的结构。对按钮、复选框、菜单和标准输入框来说，这比让模型从像素里猜目标可靠得多。

但 `find` 必须带定向 `query`，同时控制树深度和节点数。**“UIA 优先”不等于“全树 dump 优先”。**

### OCR：补充文字，不替代控件状态

当 UIA 找不到目标，或者某个窗口只暴露了很少的控件信息时，我会用 OCR 查找明确文字。

OCR 适合回答“目标文字在哪里”，但遇到开关是否选中、按钮是否禁用、两个相同文字分别属于哪个区域时，仍然需要结合结构或其他证据。

### 截图：只回答视觉问题

截图适合处理结构无法表达的信息：

- 自绘界面、游戏、画布和无控件窗口。
- 布局错位、颜色、间距和像素级对齐。
- 视觉回归与图表检查。
- 必须根据画面定位的目标。

遇到 CAPTCHA 或人工验证时，也不是让 AI 反复截图尝试，而是停下来交给人完成。

## 一次开关操作的正确循环

一个原生窗口里的开关任务，我现在按下面的顺序执行：

1. 用带 `query` 的 UIA `find` 找目标，不扫整棵树。
2. 读取元素角色和当前状态，确认不是同名控件。
3. 通过元素 ID 调用或点击。
4. 用 `wait_for` 等待目标元素或文字状态变化。
5. 只有状态结构无法说明结果时，才补 OCR 或截图。

关键变化是第 4 步：**验证操作结果，不等于再截一张图。**

浏览器也是同样的思路。表单填入后读取字段值，点击后等待目标 URL 或元素出现，比连续截图更直接，也更容易判断失败发生在哪一步。

## 这些数字不能直接当成通用基准

上面的数字来自我在 **2026-10-21** 对当时工具链的实测记录，用来比较量级，不是所有模型和工具的固定价格。

实际成本还会受这些因素影响：

- 截图分辨率、图片编码和模型的视觉计费方式。
- UIA 树深度、节点数量和返回字段。
- 网页 DOM 与 a11y 树的复杂度。
- 操作失败后的重试次数。
- 工具结果是否会持续进入后续上下文。

因此，这篇文章真正想保留的不是“某个控件一定花多少 token”，而是这条选路纪律：

> **浏览器先 CDP，桌面先 UIA；UIA 不足用 OCR，视觉问题才截图。**

再配两条限制：`find` 必须定向，验证优先读取状态。

截图仍然是必要工具，但它应该回答“看起来是否正确”，而不是代替 AI 理解每一个按钮和输入框。把结构、文字和像素分开使用，才能同时减少 token、重试和误点击。
